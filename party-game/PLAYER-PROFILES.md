# TASK 014 A — локальные профили и статистика

База: `e24058fd59920d1e8b4d7f2b9c0517eb90454977` (v72). Новая сборка: v73.

## Профили и интерфейс

`player-profiles.js` хранит модель и атомарные операции, `profile-views.js` —
выбор, создание и статистику. Главное меню: Продолжить → Новая игра →
Статистика → Настройки. На чистом устройстве нет автоматически созданных
профилей. Два разных профиля обязательны для новой партии.

Имя нормализуется NFKC, пробелы сжимаются, края обрезаются. Предел — 24
Unicode code points; сравнение имён без регистра. Вывод экранируется. Палитра
содержит восемь фиксированных цветов; произвольный CSS не принимается.
Совпадающие цвета разных профилей разрешены. Цвет лампочки и активной рамки
идёт из CSS-переменной `--profile-color`, активность определяет прежний движок.

ID профиля — 128 бит из Web Crypto. Матч получает `matchId` и
`profileMatch: {version:1, storeId, sequence, participants:[{id,name,color},…]}`.
`game.teams` сохраняется. Имена и цвета фиксируются на время партии;
положение игрока не является идентичностью. «Сыграть ещё» сохраняет прежний быстрый повтор с выбранной парой. Если
профили ещё не выбраны (например, после старой партии), открываются настройки.

## Хранилище

Новый ключ — `kvip-player-profiles:v1`, формат:

```js
{
  version: 1,
  storeId: '128-bit hexadecimal ID',
  nextSequence: 1,
  settledThrough: 0,
  profiles: [{id, name, color, createdAt}],
  totals: {
    [profileId]: {
      matches, wins, losses, draws, points, turns,  // assigned tasks
      modes: {[modeId]: {rounds, success, points, methods?}}  // assigned tasks for mode
    }
  },
  recent: [{sequence, completedAt, profileIds, scores, turns}],
  lastPair: [profileId, profileId]
}
```

Все агрегаты, результат и watermark пишутся одним `localStorage.setItem`,
после чего строка перечитывается для подтверждения. Ошибка не считается
успешной записью. Повтор после сбоя подтверждения сначала читает реальный
архив и не удваивает уже записанный результат. Новая схема не изменяет
`iskra-party:v1`, корневую `version:1` и `iskra-party:recovery:v1`.

Счётчик резервируется до создания партии без игрового `Math.random`.
`settledThrough` отвергает повтор учтённого или более старого матча, даже
после удаления его краткой записи. Схема предназначена для существующей
модели одной текущей партии на устройстве. Одновременная игра в нескольких
вкладках не является отдельным поддерживаемым режимом; облачной синхронизации
и независимого импорта старых снимков нет.

### Расширение статистики новыми игровыми режимами

Итоги хранятся **для каждого профиля по ID режима**, а не по фиксированной позиции игрока.
Для новых режимов и способов «Секретки» нет отдельного списка из восьми названий в коде статистики:
достаточно, чтобы новый режим при завершении раунда записывал свой безопасный lowercase ID
(латинские буквы, цифры, дефис или подчёркивание) и реальный итог в `game.history`.
Для режима с одним получателем история хранит `recipientIndex` и знаковую `awarded`;
для режима с несколькими получателями — `deltas` и `recipients` для каждого игрока.
Дополнительно одновременные режимы записывают `assignedIndices:[0,1]`,
потому что совместное назначение задания не зависит от выплаты очков.
Это общий контракт статистики, не отдельная ветка для каждого нового режима.
Персональные агрегаты появляются автоматически. Исторические данные режима, позднее удалённого
из игрового каталога, сохраняются, а в UI при отсутствии названия показывается его ID.
Проверка блокирует опасные имена свойств объектов и некорректные ключи.

При создании новой профильной партии запись основного snapshot в `iskra-party:v1`
обязательно должна подтвердиться **до запуска игрового экрана**. При отказе хранения
прежняя партия и её RAW восстанавливаются; пропуск зарезервованного номера
партии допустим, но новая партия не объявляется начатой.

В `recent` остаются последние 100 результатов без текстов заданий и без
`game.history`. Пожизненные итоги не обрезаются. Служебная дедупликация —
два целочисленных счётчика и store ID. Размер зависит от числа профилей и
ограниченной истории, а не числа сыгранных партий. Тест 10 000 партий с
тремя профилями: **16 590 байт UTF-8** (около 33 КБ строк UTF-16 до накладных
расходов браузера). Профили автоматически не удаляются.

## Когда и что считается

Запись вызывается после реального завершения и сохранения партии,
вне render/showResults. При запуске незаписанный завершённый снимок повторяет
попытку. Пока запись не удалась, завершённый матч нельзя заменить или удалить
кнопками меню/новой игры. Есть явная повторная запись. Если после перезапуска
запись всё ещё не удалась, открываются результаты с сообщением об ошибке.

Победы/поражения/ничьи берутся из окончательного `game.scores`; учитываются
только завершённые партии. Порог очков проверяется после ответного хода,
завершение по ходам сохраняет возможность ничьей. Незавершённая партия не
добавляет статистику.

Очки по режимам — фактические знаковые дельты из истории, без повторного
расчёта наград. Для обычного режима используется `recipientIndex`, для
«Примерно» — оба `deltas`. Сумма дельт сверяется с конечным счётом перед записью.
Риск сохраняет отрицательную дельту, базовый успех без усложнения — фактическую
базовую награду, Блиц — реальный исход движка полного набора. В новых строках
добавлены `setterIndex`, `guesserIndex`, `methodId`; «Секретка» хранит основной
режим и отдельные агрегаты rounds/success/points по фактическим способам.

Персональные задания (поле `turns`) — число задач, **предложенных
профилю**. В одиночных режимах задание назначено загадывающему;
`modes[id].rounds` — число таких заданий, `success` — успешные,
`rounds-success` — неудачные. Если игра состоит только из обычных
чередующихся заданий, то 10 партий по 30 ходов дадут каждому по
150 заданий, а не 300.

**«Примерно» — общее задание:** каждое выпавшее числовое задание
учитывается **обоим** профилям, поскольку отвечают оба. У каждого
оно может независимо попасть в «Верно» или «Неверно» согласно
`recipients`. Например, если среди 30 ходов два — «Примерно», по
одному на каждом формальном ходу, то у каждого будет 16 заданий
(14 обычных + 2 общих). В режиме «Примерно» реальное начисление
очков по `deltas` тоже остаётся индивидуальным.

В будущих одновременных режимах история может указать
`assignedIndices:[0,1]`, не добавляя исключение в код статистики.
При отсутствии поля только «Примерно» автоматически считается
совместным; остальные режимы назначаются владельцу хода. Нельзя
смешивать совместное участие и совместное получение очков:
`deltas` определяет очки, `assignedIndices` — кому выпала задача.

В разделе режимов возможны записи с 0 заданиями, но
ненулевыми очками, если очки получил не загадывающий.

Формальный владелец хода вычисляется по `startingTeamIndex` и
позиции, а `setterIndex` проверяется на соответствие. Он не меняет
того, что в «Примерно» задание совместное. Для него оба игрока
получают +1 к личному числу заданий и каждый собственный результат
из `recipients`. Для остальных режимов `taskSuccess` /
`correct` определяет результат основного задания независимо от
бонуса усложнения. Успешность в роли отгадывающего можно позже
выделить отдельно, не меняя смысл личных заданий.
Процент побед = победы / все завершённые партии, включая ничьи
в знаменателе.

## Совместимость и проверки

Старым партиям не создаются ID и профили по именам. Их Continue, текущая
карточка, политики V1–V5, пауза и recovery остаются прежними. Загрузка старого
снимка не записывает RAW и не создаёт новый архив. Повреждённая или будущая
версия архива профилей защищена от записи; отсутствие профилей не блокирует
Continue старой партии. Back в создании возвращает список, следующий Back
закрывает панель; Back в статистике возвращает меню.

Обязательные проверки добавлены в `quip-game.yml`: доменные тесты профилей,
10 000 результатов, ошибки/повтор записи, новый Chromium UI/offline сценарий
320×568, 390×844, 412×915, desktop и landscape. Три диагностических изображения
попадают в CI artifact `quip-browser-screenshots/quip-profiles`. Существующие
игровые тесты создают явные тестовые профили; production boot их не создаёт.

PWA v73 включает оба новых модуля и согласованные URL CSS/JS в precache.

Физическое Android-устройство не проверялось: системный Back моделируется
через browser history в Chromium. Редактирование/удаление профилей и облачная
синхронизация остаются за пределами этого MVP.
