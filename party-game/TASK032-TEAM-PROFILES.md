## Архитектура участников

Четыре селектора используют существующие `profileStore`, `QUIP_PROFILES_KEY`, создание профиля, палитру и диалог `openProfilePanel`. Командная цель диалога — явный объект `{format:'teams-2x2',slot:0..3}`; два `selectedProfileIds` дуэли и выбор статистики сохраняют прежний смысл. Выбор четырёх разных существующих ID проверяется интерфейсом и повторно через настоящий `readProfileStore` внутри блокировки START. Выбор формата не фокусирует input и не открывает диалог.

Новые партии имеют `teamFormat.version=2`, `statsPolicy='separate-team-profiles-v1'` и строго проверяемую `profileBinding.version=1`: storeId и два массива по два `{id,name,color}`. Имена/цвета — снимок для этой партии; идентичность — ID, не имя. Даже одинаковые имена не объединяют людей. Три исходных RNG-вызова выбора стартовых ролей сохранены; привязка не расходует игровой RNG.

Старый header v1 по-прежнему строго допускает только прежние поля и `excluded-from-duel-profiles`. При загрузке он не мигрирует, не получает ID по именам и не начисляет новую статистику. Архивы сохраняют точные исходные записи. Продолжение связанной партии проверяет наличие её storeId и четырёх profileId; при отсутствии профилей RAW остаётся защищённым и требуется восстановление соответствующих профилей.

## Единственный источник командной статистики

Новый конверт командной записи v2 содержит `profileResults`: версионированные неизменяемые вклады завершённых партий. Он находится **в том же командном RAW**, что игра, и подтверждается прежними SHA-256, Web Lock, журналом и native IndexedDB receipt. Формат receipt/его DB и внешний storage envelope v1 не меняются. Дополнительно проверяется переход: привязку текущей партии менять нельзя, записанные результаты нельзя удалить/переписать; новый вклад должен точно совпадать с пересчётом текущего подтверждённого результата.

Перед проекцией выполняется полный валидатор игры, истории, очков, ролей и правил. Вклад появляется только при `phase='results' && reviewConfirmed===true`. START, незавершённая партия, просмотр счёта, редактирование до финального подтверждения и тай-брейк до его подтверждения не начисляют статистику. Итог и все четыре вклада записываются одной транзакцией. При прерывании существующий журнал/receipt сохраняет проверяемые before/after; приложение не показывает ложный успех. Явное восстановление before/after восстанавливает игру и статистику вместе.

Постоянный matchId — ключ идемпотентности. Повторный вход/перезапуск не добавляет запись; экспортированный и текущий экземпляры одного вклада объединяются по ID, а несовпадающие версии одного результата отвергаются. При очистке игрового архива ledger сохраняется. Конкурирующие подтверждения проходят тот же native CAS: один победитель, другая вкладка получает conflict.

## Смысл показателей

Раздел «1 НА 1» продолжает читать прежние totals без изменения значений. Раздел «2 НА 2» показывает завершённые игры, победы/поражения/ничьи, загадывания, отгадывания, совместные числовые вопросы, командные тай-брейки и результаты режимов по реальным ролям. Успех задания подписан как **командный успех в соответствующей роли**. Командный счёт показывается отдельно; личных очков из него не создаётся.

«Примерно» учитывается как совместное участие всех четырёх, без выдуманных индивидуальных ответов/успехов. Тай-брейк — совместное участие; его решающий командный балл не превращается в личные очки. Победа/поражение/ничья определяется финальным подтверждённым счётом команды для обоих её участников.

## Экспорт и импорт

Обычный экспорт профилей объединяет проверенный командный ledger с ранее импортированными вкладами и включает все показатели обоих форматов. При наличии командных результатов создаётся явный backup v2 с payload профилей v2 и `teamStatistics.version=1`. Без таких данных старый v1 остаётся v1. Профили живого приложения не переписываются из-за завершения командной игры: snapshot v2 создаётся для экспорта; при явном импорте все ID, дуэльные значения и командные вклады восстанавливаются **одной существующей атомарной записью профилей**, с прежним pending-marker, readback и защитной копией. Вторая база пользователей и новая процедура аварийного отката не создаются.

Импорт проверяет несовпадающие результаты одного ID и не может лишить незавершённую связанную командную партию её участников. Архив другого storeId не приписывает прежние игры совпадающим именам. Экспорт защитной копии сохраняет её точное прежнее содержимое; он явно отличается от полного текущего экспорта. Игровые партии экспортируются прежней отдельной кнопкой, статистика обоих форматов входит в экспорт профилей.

- Чтение неизменённого архива профилей сохраняет идентичность уже проверенного объекта, не отменяя валидацию. Открытие списка профилей поэтому не сбрасывает presentation-cache TASK029. Настройки, профили, каталоги и ссылки на функции входят в stamp; контролы рендерятся прежним кодом. Временные wrappers снимаются в finally, START и игра всегда используют полные исходные API.

На этапе первичной реализации локально проходят 11 новых контрактных тестов и существующие проверки профилей/backup/командного движка. Новые сценарии покрывают словоформы, строгие v1/v2, три RNG-вызова, победу/поражение/ничью, совместные задания, исправления истории, тай-брейк, неизменность дуэльных totals, идемпотентность, архивы, CAS, три вида прерывания записи с обоими вариантами восстановления и полный backup round-trip.

В обязательный CI добавлены четыре TASK032 browser job: 320×568, 390×844, 412×915, 844×390; Android UA/mobile/touch/CPU4/n20, нативные START/сохранения/receipt, четыре селектора/создание/focus, грамматика, источники и разделители, реальные результаты, cold offline, повторное подтверждение, прерывание финальной записи и импорт файла. Скриншоты и сырые `evidence.json` сохраняются в `quip-task032-{width}`. Полные CI-результаты и численные измерения будут зафиксированы после проверки фактического Head; реализация пока не объявляется завершённой.

Прежние тесты не выключаются. Исторические проверки исходников обращают только точные TASK032 hunks; отдельный новый guard проверяет весь наследуемый runtime вне этих изменений. PWA-проверки требуют все **54** текущих скрипта, включая новый чистый модуль статистики. Старые names-only партии создаются под историческим UI до обновления, а не подменяются новыми v2-партиями при проверке старого runtime.

## Границы и ограничения

Не меняются игровые награды, время, роли/их RNG, правила режимов, словари G26–G36, принятый игровой CSS v88, дуэльные слоты, запись командного черновика только при START и защитные механизмы хранилища. Worker меняет только версии ресурсов и уникальный cache name; install/activate/fetch прежние. `manifest.webmanifest` не меняется.

Ledger не обрезается автоматически: сохраняются существующий общий лимит RAW 1 MiB и строгая граница 4 096 вкладов. При превышении запись должна отказать безопасно, а не потерять статистику или ослабить receipt. Старые версии приложения не обязаны понимать новые v2-партии/экспорты; старые v1-партии продолжаются новой версией. Физический Android не тестировался; обязательные измерения относятся к браузерной эмуляции. Дополнительные резервные ветки, отдельные аварийные релизы и новая историческая матрица не создаются.
