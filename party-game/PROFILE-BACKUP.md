# КВИП — TASK 016: локальные резервные копии профилей

## Пользовательский путь

Меню → **Настройки** → **Резервное копирование**.

- **Создать резервную копию** скачивает `kvip-profiles-YYYY-MM-DD.json` стандартным механизмом браузера. Никаких сетевых запросов, аккаунтов или серверного хранения файла.
- **Восстановить из файла** открывает системный выбор JSON (до 4 МиБ в UTF-8). Проверка и сравнение архивов ничего не записывают.
- Предпросмотр показывает дату файла, количество профилей, имена, цвета, игры/победы/поражения/ничьи и компактное сравнение с устройством.
- На пустом устройстве нужна отдельная кнопка восстановления. Если архив существует, сначала **Продолжить**, затем предупреждение, самостоятельный флажок согласия и **Заменить статистику**. Отмена, фон, Escape и Android Back закрывают панель без изменения данных.
- Идентичный архив распознаётся без записи. Старый, новый, разошедшийся и архив другого устройства классифицируются, но **никогда не складываются**.

Полная копия игры не создаётся: текущая партия, ещё не записанный результат, игровые настройки, звук и история всех карточек не входят в файл. Экспорт содержит только уже учтённую профильную статистику. При ошибке памяти не сообщается об успехе.

## Данные и совместимость

Экспортируется весь валидированный `kvip-player-profiles:v1`: постоянные ID, имена/цвета/даты, `storeId`, `nextSequence`, `settledThrough`, `profiles`, `totals`, `recent` (до 100), `lastPair`. Сохраняются счётчики тай-брейков v74/v75, способы Секретки и допустимые неизвестные будущие поля. Старый архив v73 без необязательных счётчиков принимается. Модель профилей не мигрируется.

Формат файла: `{kind:"kvip-profile-backup",version:1,exportedAt,sha256,payload}`. SHA-256 вычисляется Web Crypto по точному `JSON.stringify(payload)`. Это проверка случайного повреждения, **не электронная подпись или доказательство происхождения**. Самостоятельно отредактированный файл с пересчитанной суммой всё равно проходит структурный `validateProfileStore`.

`recent` усечён, а одинаковый `storeId` не доказывает общую историю двух телефонов. `older/newer` сравнивают watermark, не подтверждают происхождение. Автоматическое объединение запрещено.

## Ядро и API

`profile-backup.js` продолжает исходное ядро PR #82; UI вынесен в `profile-backup-view.js`. В `app.js` добавлена только регистрация его обработчиков.

- `await createProfileBackupText(store, exportedAt?)`: независимый JSON-снимок, валидация, SHA-256, ограничение размера; без записей.
- `await inspectProfileBackupText(text, currentRaw?)`: read-only проверка формата/версии/размера/JSON/контрольной суммы/схемы действующего и входного архива; `relationship`, `summary`, `current`, `sourceRaw`.
- `await restoreProfileBackupText(storage,text,{allowReplace,expectedRaw,expectedGameRaw})`: повторная проверка и контролируемая полная замена. UI передаёт точные строки обоих ключей из предпросмотра; изменение между просмотром и подтверждением запрещает запись и создание recovery. Повторная проверка после асинхронного SHA-256 ловит изменение во время операции.
- `inspectProfileBackupRecovery(storage)` и `clearProfileBackupRecovery(storage,exactReviewedRaw)`: проверка/осознанное освобождение единственного защитного слота.

## Транзакция, recovery и ошибки памяти

Перед изменением профилей сохраняется точный прежний RAW в одном `kvip-player-profiles:import-recovery:v1` и проверяется чтением. Существующая копия **никогда не перезаписывается автоматически**. Повтор после подтверждённого rollback может повторно использовать её только при полном совпадении прежнего RAW. Копия другого состояния блокирует замену.

В настройках занятого recovery есть отдельное сохранение в переносимый JSON. Только после скачивания, отдельной отметки «Я сохранил файл» и явного подтверждения можно освободить слот. Браузер не доказывает сохранность скачанного файла; это решение пользователя. Повреждённая копия автоматически не удаляется.

Перед записью основного профильного ключа создаётся и проверяется один маленький `kvip-player-profiles:import-pending:v1`. После записи профилей выполняется точное чтение, затем проверенное удаление маркера. При ошибке записи/чтения выполняется rollback прежнего RAW (либо удаление нового ключа для пустого устройства). Неподтверждённый rollback или невозможность подтвердить окончание блокирует **все** профильные операции через `readProfileStore`/`writeProfileStore`; постоянный маркер сохраняет блокировку после перезапуска. В текущем процессе дополнительно действует флаг неопределённого состояния.

В таком аварийном случае нельзя автоматически выбирать между прежними и новыми данными: UI показывает блокировку, позволяет сохранить прежний recovery, не показывает успех и не разрешает новую партию/начисление/создание профиля. Снятие аварийной блокировки требует ручной проверки; автоматического разрушительного «починить» нет. При полном отказе памяти нельзя гарантировать сохранение новых записей; успешного завершения в этом случае нет.

Число служебных ключей фиксировано (одна копия + один короткий маркер), журнал импортов не растёт. При штатном завершении маркер отсутствует. Иные игровые ключи импорт не изменяет.

Операция синхронно проверяет исходные строки непосредственно перед записью, но Web Storage не имеет межвкладочного compare-and-swap. Два одновременно открытых экземпляра приложения не должны импортировать/играть параллельно; полноценная многовкладочная транзакционная БД не добавлялась.

## Партии и защищённые сохранения

Любая `game` в `iskra-party:v1` блокирует восстановление: ready, таймер, пауза, тай-брейк и results. Неизвестная версия, повреждённое сохранение, несовместимые настройки/память заданий также запрещают импорт. `iskra-party:recovery:v1` не изменяется.

Для оставшегося **завершённого** результата предпросмотр предлагает **Открыть результаты партии**. Это только навигация. Игрок отдельно нажимает обычную кнопку **В меню**; существующий `saveCompletedProfileResult` сначала проверяет запись результата, и при ошибке оставляет его на экране. Затем обычная игровая навигация архивирует историю и закрывает партию. После этого нужно снова выбрать файл. Если сохранение при закрытии не удалось и RAW всё ещё содержит game, импорт по-прежнему блокируется. Незавершённые партии этот путь не удаляет.

Экспорт доступен при активной партии, но не включает её незаписанный результат. Импортированный watermark запрещает повторное начисление давно учтённых результатов даже после удаления старых строк `recent`.

## Проверки и PWA

Ветка объединена с актуальным `main` v75, продолжает PR #82. Новая версия PWA v76; оба модуля добавлены в precache, версии каждого изменённого runtime-файла в HTML и SW совпадают. Словари/каталоги не редактировались.

`profile-backup.test.cjs`: round-trip, ID/режимы/тай-брейки/будущие поля/v73, дедупликация, checksum/схема/версии/UTF-8 размер, разные истории, stale preview и SHA race, quota/readback, recovery и его занятость, повтор после rollback, постоянная блокировка и перезапуск, все фазы партии.

`profile-backup-browser.cjs`: реальные file chooser/download, предпросмотр/согласие/отмена/Back/Escape, 320×568 / 390×844 / 844×390, touch, офлайн cold reload → экспорт/импорт → перезапуск → выбор профилей/новая партия; отдельное закрытие уже учтённого результата, повреждения и stale preview. Три диагностических снимка. Существующие Browser suites дополнительно проверяют тай-брейк и видимость карточки.

Запуск: `node --test party-game/tests/profile-backup.test.cjs`; HTTP-сервер и Chromium: `node party-game/tests/profile-backup-browser.cjs`. Точные Head SHA, результаты обязательного CI и ссылки на снимки приведены в PR. Эмуляция Chromium не заменяет проверку на физическом Android.
