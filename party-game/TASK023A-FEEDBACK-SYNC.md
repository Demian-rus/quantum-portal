# TASK 023A — проект автоматического сбора оценок и отключённый локальный прототип

Issue [#110](https://github.com/Demian-rus/quantum-portal/issues/110), база `4bb6e67d8bed60f03459f31b14e6168ea996048b`, опубликованная PWA v87. Границы этапа закреплены [архитектором](https://github.com/Demian-rus/quantum-portal/issues/110#issuecomment-6401391970). Проверка тарифов: 25.10.2026, USD без налогов; это расчёт вариантов, не согласие на платную подписку.

## Что поставлено и что работает сейчас

023A содержит общий wire-протокол, отдельный браузерный клиент очереди, локальный HTTP/SQLite стенд, owner-only JSON экспорт, тесты и этот проект. Все опубликованные runtime-файлы v87, включая `index.html`, `sw.js`, TASK022, scoring, risk, RNG, профили, резервные копии и каталоги, сохранены побайтово. CI только дополнен проверками нового кода.

**В опубликованной игре автоматическая отправка пока не включена.** Новые модули намеренно не подключены к HTML/CORE, `DEFAULT_CONFIG.enabled=false`, endpoint отсутствует. Поэтому не выпускается кандидат v88, ничего не загружается и не отправляется, installId не создаётся. Старые жалобы, одобрения, Web Share и JSON работают прежним образом. Это безопасная стадия A; сервер и включение в PWA — отдельная 023B после приёмки архитектуры, доступа владельца и расходов.

В тестовом стенде включённый клиент умеет автоматически работать через `start()`: запуск, события online/storage/visibilitychange и опрос раз в 15 секунд. При закрытой PWA выполнения нет; доставка продолжится при следующем открытии. Background Sync и push не требуются. Нового пользовательского UI в этом PR нет; API статуса подготовлен для 023B.

## Протокол v1 и API

Один запрос `POST /v1/feedback`, JSON ≤2048 UTF-8 байт, без cookies/Authorization; CORS разрешает только точный origin PWA. HTTPS обязателен; HTTP loopback разрешается только явно для локального стенда. Клиент использует `credentials:omit`, `redirect:error`, `referrerPolicy:no-referrer`, `cache:no-store`, timeout 10 секунд. Список полей закрыт и проверяется с обеих сторон.

```json
{
  "version": 1,
  "installId": "b1d3ab12-6e87-4e66-8c09-0d90765bc2e4",
  "revision": 12,
  "eventId": "b1d3ab12-6e87-4e66-8c09-0d90765bc2e4:12",
  "item": {"cardId": "word-000001", "pack": {"id": "general", "version": 7}},
  "rating": "report",
  "reason": "ambiguous",
  "comment": "Формулировка неоднозначна"
}
```

`rating`: approve/report/deleted. Для approve/deleted reason и comment равны null. В report причина — одно из error/ambiguous/hard/duplicate/theme/other. Комментарий нормализован NFKC, пробелы свёрнуты; ≤160 Unicode-символов и ≤640 UTF-8 байт. Управляющие символы, bidi-контролы и одиночные суррогаты отклоняются. Содержимое считается недоверенным текстом; будущая панель обязана выводить его через textContent, не HTML. Стенд отдаёт только JSON с nosniff.

installId — случайный UUIDv4 из Web Crypto, не игровой RNG, не профиль и не идентификатор человека. Номер revision растёт на устройстве; время телефона не определяет порядок. eventId выводится из этих двух полей. Сетевой item не содержит текста карточки, режима, игроков, времени, версии приложения или данных партии. Исторические карточки с ID допустимы; проверка наличия ID в известных версиях каталога обязательна на production backend 023B. Локальный стенд пока проверяет схему/синтаксис, не подключает игровые каталоги.

После durable commit сервер отвечает **200**:

```json
{"version":1,"installId":"b1d3ab12-6e87-4e66-8c09-0d90765bc2e4","revision":12,"eventId":"b1d3ab12-6e87-4e66-8c09-0d90765bc2e4:12","status":"applied"}
```

При повторе — status=duplicate. Только точное совпадение этих полей и допустимого статуса подтверждает доставку. Пустой 204, неожиданные поля, неверный eventId, HTML, слишком большой или повреждённый ответ ACK не заменяют. Ответ ограничен 1024 байтами при чтении потока.

Коды: 400/413/415 — схема/размер/тип; 403 — origin; 409 — более старая revision или повтор revision с иным содержимым; 429 — ограничение частоты с Retry-After; 503 — временная недоступность/ёмкость. 4xx, кроме 408/425/429, сохраняют halted до явного `resume()` после устранения причины. Нет тихой смены installId при конфликте. Сетевые ошибки, неправильные ACK и 5xx повторяются с backoff: от 5 секунд до часа + криптографический jitter ≤999 ms, Retry-After 429/503 учитывается до суток. Состояние ожидания сохраняется после перезапуска. Один цикл отправляет максимум 10 событий.

## Очередь, замены, удаления и сбои

Отдельный ключ `kvip-feedback-outbox:v1`: endpoint, installId, sequence, ограниченные записи текущего состояния, pending, счётчик/срок retry, halted и время последнего подтверждённого ACK. Ключ привязан к точному endpoint: нельзя без решения о миграции отправить накопленное другому серверу.

При **первом включении** текущие оценки становятся локальным baseline, без отправки. Имена и текст задания в baseline не копируются. Старые оценки без изменения не уходят; изменение или замена после baseline создаёт новую текущую оценку. Неизменное повторное 👍 не создаёт события. Осознанный импорт старого архива не реализован и не включён молча. Редактирование реально меняет fingerprint содержимого, а не только updatedAt.

Сначала прежний журнал надёжно принимает оценку, затем очередь сверяет его с checkpoint. Перезапуск между этими шагами безопасен: изменённый журнал отличается от сохранённого baseline и восстанавливает pending. При ошибке записи очереди журналы не откатываются и не очищаются. Текст локальной ошибки не означает успешную доставку. У queue write собственные compare/readback/rollback; если откат не подтверждён, экземпляр блокируется. Повреждённый/неизвестный формат не переписывается. Для восстановления сначала экспорт/анализ, не автоматическое удаление исходного ключа.

Хранится последняя оценка карточки, а не бесконечная лента кликов. Неподтверждённые изменения одной карточки заменяют её pending с новой revision. Если прежнее событие уже в полёте, его ACK не удалит более новое. Сервер хранит одну актуальную строку `(installId,itemKey)`, обновляет её только большей revision, поэтому 👍→👎 меняет оценку, а не добавляет второй голос. Локальная очистка/удаление ранее синхронизируемой оценки порождает tombstone deleted. Удаление старого никогда не отправленного baseline не создаёт сетевых событий. После подтверждения tombstone запись из очереди удаляется; сервер сохраняет watermark против воскресшего старого запроса. Старые комментарии не сохраняются в таблице event IDs: там только hash.

Лимиты клиента: 2000 отслеживаемых карточек, 1000 pending, 2 MiB сериализованного state. При заполнении новые изменения **не вытесняют** очередь: остаются в исходных журналах и видны в `deferred`. После отправки накопленного клиент принимает отложенные изменения; заполнение не блокирует дренирование. Игровые лимиты 500+500 остаются прежними. Поведение очереди latest-state означает, что промежуточные неотправленные клики не являются отдельными аналитическими событиями.

Web Locks сериализует работу очереди между вкладками; отдельный sender-lock охватывает сетевой запрос. Без Web Locks/Web Crypto автоматическая отправка недоступна, остаются локальные журналы/JSON. Это не превращает старые синхронные игровые журналы в межвкладочную транзакционную БД: одновременное редактирование одной партии/оценок из разных вкладок по-прежнему не поддерживается. При неподтверждённом откате источников adapter обязан отказаться от чтения/отправки.

API статуса: mode=disabled/idle/pending/attention, pending, deferred, delivered, localOnly, lastAckAt, error. `delivered` — только подтверждённые текущие записи; localOnly включает baseline и legacy. Нет строки «все оценки отправлены» только по отсутствию pending. `resume()` не сбрасывает идентичность/номер revision. Удаление данных сайта создаёт новую анонимную установку, прежняя не восстанавливается; удалённый installId не позволяет стереть старые серверные данные. Поэтому 023B должна отдельно реализовать понятное серверное удаление до локального reset и сроки retention. Нельзя обещать восстановление после полного удаления данных или переполнения локального хранилища.

## Threat model и production-защита

| Угроза | Защита 023A | Обязательная работа 023B |
| --- | --- | --- |
| Повторы, потеря ACK, переупорядочивание | UUID + revision, unique event ID/hash, атомарный SQLite commit, tombstone watermark | Эквивалентная атомарная реализация D1 и интеграционная приёмка |
| Чужие поля/большой текст/инъекции | Закрытая схема, размер тела/ACK, UTF-8, prepared SQL, JSON/nosniff | Каталожная валидация, textContent в owner-панели |
| Спам/новые installId/поддельный Origin | Стенд: 30 запросов/install/min, 60/IP/min, 1000 global/min; bounded buckets, жёсткая ёмкость SQLite | Edge/WAF + общие устойчивые квоты, лимит новых установок, kill switch/метрики; нагрузочная приёмка |
| Утечка игровых данных/секретов | Белый список wire-полей; credentials omit; нет GitHub API/token; owner token только у локального сервера | Отдельный owner Access/SSO, секреты только server-side, приватный экспорт |
| Старые оценки/неподходящий backend | Baseline skip-old, endpoint binding, выключенная функция | Согласование включения, notice комментариев, политика миграции |

CORS не является аутентификацией; внебраузерный клиент подделает Origin. installId не доказывает уникального игрока: очистка данных, другой браузер и бот создают новые установки. Нельзя обещать полную защиту от накрутки без регистрации/дополнительного challenge. Рекомендуется считать такие оценки редакционными сигналами, а не достоверными голосами уникальных людей; автоматического удаления карточек по ним не делать. Если атака потребует Turnstile/challenge, это отдельное UX-решение, а не скрытая зависимость текущей игры.

Staging-сервер привязан к 127.0.0.1 и не предназначен для reverse proxy в интернет. Его in-memory rate buckets сбрасываются при рестарте и не распределены по инстансам. Ёмкость — 10000 vote-watermark строк и 100000 event-hash строк; при превышении 503 сохраняет прежние данные. Удаления не вычищают watermark, иначе старые повторы воскреснут. Стенд не делает TTL, физическое стирание SQLite/WAL или удаление установки — это остаётся явной production-задачей, не скрытым обещанием приватности.

Предлагаемая политика для согласования: комментарии/подробные жалобы 90 дней, обезличенные агрегаты 12 месяцев; отдельное отключение/удаление установки с отзывом её дальнейших событий. Для фактического удаления нужны expiry/revocation установки и порядок удаления backup/logs, чтобы устаревший offline-клиент не восстановил стёртый контент. Пока это **предложение**, не реализованная retention-гарантия. Raw IP не входит в SQLite/экспорт; на облаке IP неизбежно видит ingress-провайдер, для квот использовать короткоживущий server-side hash и минимальное логирование, без тела комментариев в logs.

## Локальная приёмка и дальнейшее включение

Node ≥22.13 (node:sqlite встроен; на 22.x экспериментальный API). Стенд использует SQLite WAL + synchronous FULL; ack формируется после COMMIT. Запуск — только loopback, owner token передаётся окружением и не кладётся в git/клиент:

```sh
node --test party-game/tests/feedback-sync.test.cjs
KVIP_OWNER_TOKEN='<случайный локальный секрет не короче 32 символов>' node party-game/feedback-sync/local-server.cjs
```

По умолчанию база в `/tmp/kvip-feedback-023a.sqlite`; для повторяемого долговременного локального стенда задайте `KVIP_FEEDBACK_DB` на отдельный путь. Это не долговременное облачное хранилище. `GET /owner/export` с Bearer owner token возвращает агрегаты и максимум 1000 актуальных жалоб; пагинация/полный owner-архив — 023B. Токен не передаётся в ingestion и не вводится в PWA. Браузерный доступ к owner endpoint у стенда запрещён, используйте локальный CLI.

Browser тест сам поднимает одноразовый loopback-сервер, использует настоящий origin приложения и реальные производственные журналы. Модули добавляются **только тестом**, включая после offline reload; в published cache они не появляются. Проверяются инертный gate, CORS/ACK, offline→reload→online, unchanged JSON/private storage, замена/удаление, Web Locks в двух вкладках. Скриншоты не создаются: UI не менялся. Для существующей PWA все прежние Browser/Logic/Gameplay/Smoke/upgrade проверки сохранены.

Будущий adapter 023B должен: дождаться успешного сохранения/удаления/очистки через прежнее ядро; проверить `cardReportsBlocked || cardApprovalsBlocked`; читать через существующие `readCardReports/readCardApprovals`, затем вызвать reconciliation. Повторный poll/boot закрывает окно сбоя после сохранения. Ошибка sync не должна превращать уже сохранённую локальную оценку в ошибку игрового действия. Нельзя читать журналы посреди незавершённой их замены или отправлять их при заблокированном rollback.
