## Что поставлено и что работает сейчас

023A содержит общий wire-протокол, отдельный браузерный клиент очереди, локальный HTTP/SQLite стенд, owner-only JSON экспорт, тесты и этот проект. После интеграции все опубликованные runtime-файлы v88, включая `index.html`, `sw.js`, TASK024/022, scoring, risk, RNG, профили, резервные копии и каталоги, сохранены побайтово. CI только дополнен проверками нового кода.

**В опубликованной игре автоматическая отправка пока не включена.** Новые модули намеренно не подключены к HTML/CORE, `DEFAULT_CONFIG.enabled=false`, endpoint отсутствует. Версии ресурсов и CACHE v88 сохраняются; ничего не загружается и не отправляется, installId не создаётся. Старые жалобы, одобрения, Web Share и JSON работают прежним образом. Сервер и включение в PWA — отдельная 023B после приёмки архитектуры, доступа владельца и расходов.

В тестовом стенде включённый клиент умеет автоматически работать через `start()`: запуск, события online/storage/visibilitychange и опрос раз в 15 секунд. При закрытой PWA выполнения нет; доставка продолжится при следующем открытии. Background Sync и push не требуются. Нового пользовательского UI в этом PR нет; API статуса подготовлен для 023B.

## Протокол v1 и API

Один запрос `POST /v1/feedback`, JSON ≤2048 UTF-8 байт, без cookies/Authorization; CORS разрешает только точный origin PWA. HTTPS обязателен; HTTP loopback разрешается только явно для локального стенда. Клиент использует `credentials:omit`, `redirect:error`, `referrerPolicy:no-referrer`, `cache:no-store`, timeout 10 секунд. Список полей закрыт и проверяется с обеих сторон.

```json
{
  "version": 1,
  "installId": "b1d3ab12-6e87-4e66-8c09-0d90765bc2e4",
  "revision": 12,
  "eventId": "b1d3ab12-6e87-4e66-8c09-0d90765bc2e4:12",
  "item": {"cardId": "word-000001", "pack": {"id": "general", "version": 7}},
  "rating": "report",
  "reason": "ambiguous",
  "comment": "Формулировка неоднозначна"
}
```

`rating`: approve/report/deleted. Для approve/deleted reason и comment равны null. В report причина — одно из error/ambiguous/hard/duplicate/theme/other. Комментарий нормализован NFKC, пробелы свёрнуты; ≤160 Unicode-символов и ≤640 UTF-8 байт. Управляющие символы, bidi-контролы и одиночные суррогаты отклоняются. Содержимое считается недоверенным текстом; будущая панель обязана выводить его через textContent, не HTML. Стенд отдаёт только JSON с nosniff.

installId — случайный UUIDv4 из Web Crypto, не игровой RNG, не профиль и не идентификатор человека. Номер revision растёт на устройстве; время телефона не определяет порядок. eventId выводится из этих двух полей. Сетевой item не содержит текста карточки, режима, игроков, времени, версии приложения или данных партии. Исторические карточки с ID допустимы; проверка наличия ID в известных версиях каталога обязательна на production backend 023B. Локальный стенд пока проверяет схему/синтаксис, не подключает игровые каталоги.

После durable commit сервер отвечает **200**:

```json
{"version":1,"installId":"b1d3ab12-6e87-4e66-8c09-0d90765bc2e4","revision":12,"eventId":"b1d3ab12-6e87-4e66-8c09-0d90765bc2e4:12","status":"applied"}
```

При повторе — status=duplicate. Только точное совпадение этих полей и допустимого статуса подтверждает доставку. Пустой 204, неожиданные поля, неверный eventId, HTML, слишком большой или повреждённый ответ ACK не заменяют. Ответ ограничен 1024 байтами при чтении потока.

Коды: 400/413/415 — схема/размер/тип; 403 — origin; 409 — более старая revision или повтор revision с иным содержимым; 429 — ограничение частоты с Retry-After; 503 — временная недоступность/ёмкость. 4xx, кроме 408/425/429, сохраняют halted до явного `resume()` после устранения причины. Нет тихой смены installId при конфликте. Сетевые ошибки, неправильные ACK и 5xx повторяются с backoff: от 5 секунд до часа + криптографический jitter ≤999 ms, Retry-After 429/503 учитывается до суток. Состояние ожидания сохраняется после перезапуска. Один цикл отправляет максимум 10 событий.

## Очередь, замены, удаления и сбои

Отдельный ключ `kvip-feedback-outbox:v1`: endpoint, installId, sequence, ограниченные записи текущего состояния, pending, счётчик/срок retry, halted и время последнего подтверждённого ACK. Ключ привязан к точному endpoint: нельзя без решения о миграции отправить накопленное другому серверу.

При **первом включении** текущие оценки становятся локальным baseline, без отправки. Имена и текст задания в baseline не копируются. Старые оценки без изменения не уходят; изменение или замена после baseline создаёт новую текущую оценку. Неизменное повторное 👍 не создаёт события. Осознанный импорт старого архива не реализован и не включён молча. Редактирование реально меняет fingerprint содержимого, а не только updatedAt.

Сначала прежний журнал надёжно принимает оценку, затем очередь сверяет его с checkpoint. Перезапуск между этими шагами безопасен: изменённый журнал отличается от сохранённого baseline и восстанавливает pending. При ошибке записи очереди журналы не откатываются и не очищаются. Текст локальной ошибки не означает успешную доставку. У queue write собственные compare/readback/rollback; если откат не подтверждён, экземпляр блокируется. Повреждённый/неизвестный формат не переписывается. Для восстановления сначала экспорт/анализ, не автоматическое удаление исходного ключа.

Хранится последняя оценка карточки, а не бесконечная лента кликов. Неподтверждённые изменения одной карточки заменяют её pending с новой revision. Если прежнее событие уже в полёте, его ACK не удалит более новое. Сервер хранит одну актуальную строку `(installId,itemKey)`, обновляет её только большей revision, поэтому 👍→👎 меняет оценку, а не добавляет второй голос. Локальная очистка/удаление ранее синхронизируемой оценки порождает tombstone deleted. Удаление старого никогда не отправленного baseline не создаёт сетевых событий. После подтверждения tombstone запись из очереди удаляется; сервер сохраняет watermark против воскресшего старого запроса. Старые комментарии не сохраняются в таблице event IDs: там только hash.

Лимиты клиента: 2000 отслеживаемых карточек, 1000 pending, 2 MiB сериализованного state. При заполнении новые изменения **не вытесняют** очередь: остаются в исходных журналах и видны в `deferred`. После отправки накопленного клиент принимает отложенные изменения; заполнение не блокирует дренирование. Игровые лимиты 500+500 остаются прежними. Поведение очереди latest-state означает, что промежуточные неотправленные клики не являются отдельными аналитическими событиями.

Web Locks сериализует работу очереди между вкладками; отдельный sender-lock охватывает сетевой запрос. Без Web Locks/Web Crypto автоматическая отправка недоступна, остаются локальные журналы/JSON. Это не превращает старые синхронные игровые журналы в межвкладочную транзакционную БД: одновременное редактирование одной партии/оценок из разных вкладок по-прежнему не поддерживается. При неподтверждённом откате источников adapter обязан отказаться от чтения/отправки.

API статуса: mode=disabled/idle/pending/attention, pending, deferred, delivered, localOnly, lastAckAt, error. `delivered` — только подтверждённые текущие записи; localOnly включает baseline и legacy. Нет строки «все оценки отправлены» только по отсутствию pending. `resume()` не сбрасывает идентичность/номер revision. Удаление данных сайта создаёт новую анонимную установку, прежняя не восстанавливается; удалённый installId не позволяет стереть старые серверные данные. Поэтому 023B должна отдельно реализовать понятное серверное удаление до локального reset и сроки retention. Нельзя обещать восстановление после полного удаления данных или переполнения локального хранилища.

## Threat model и production-защита

| Угроза | Защита 023A | Обязательная работа 023B |
| --- | --- | --- |
| Повторы, потеря ACK, переупорядочивание | UUID + revision, unique event ID/hash, атомарный SQLite commit, tombstone watermark | Эквивалентная атомарная реализация D1 и интеграционная приёмка |
| Чужие поля/большой текст/инъекции | Закрытая схема, размер тела/ACK, UTF-8, prepared SQL, JSON/nosniff | Каталожная валидация, textContent в owner-панели |
| Спам/новые installId/поддельный Origin | Стенд: 30 запросов/install/min, 60/IP/min, 1000 global/min; bounded buckets, жёсткая ёмкость SQLite | Edge/WAF + общие устойчивые квоты, лимит новых установок, kill switch/метрики; нагрузочная приёмка |
| Утечка игровых данных/секретов | Белый список wire-полей; credentials omit; нет GitHub API/token; owner token только у локального сервера | Отдельный owner Access/SSO, секреты только server-side, приватный экспорт |
| Старые оценки/неподходящий backend | Baseline skip-old, endpoint binding, выключенная функция | Согласование включения, notice комментариев, политика миграции |

CORS не является аутентификацией; внебраузерный клиент подделает Origin. installId не доказывает уникального игрока: очистка данных, другой браузер и бот создают новые установки. Нельзя обещать полную защиту от накрутки без регистрации/дополнительного challenge. Рекомендуется считать такие оценки редакционными сигналами, а не достоверными голосами уникальных людей; автоматического удаления карточек по ним не делать. Если атака потребует Turnstile/challenge, это отдельное UX-решение, а не скрытая зависимость текущей игры.

Staging-сервер привязан к 127.0.0.1 и не предназначен для reverse proxy в интернет. Его in-memory rate buckets сбрасываются при рестарте и не распределены по инстансам. Ёмкость — 10000 vote-watermark строк и 100000 event-hash строк; при превышении 503 сохраняет прежние данные. Удаления не вычищают watermark, иначе старые повторы воскреснут. Стенд не делает TTL, физическое стирание SQLite/WAL или удаление установки — это остаётся явной production-задачей, не скрытым обещанием приватности.

Предлагаемая политика для согласования: комментарии/подробные жалобы 90 дней, обезличенные агрегаты 12 месяцев; отдельное отключение/удаление установки с отзывом её дальнейших событий. Для фактического удаления нужны expiry/revocation установки и порядок удаления backup/logs, чтобы устаревший offline-клиент не восстановил стёртый контент. Пока это **предложение**, не реализованная retention-гарантия. Raw IP не входит в SQLite/экспорт; на облаке IP неизбежно видит ingress-провайдер, для квот использовать короткоживущий server-side hash и минимальное логирование, без тела комментариев в logs.

## Локальная приёмка и дальнейшее включение

Node ≥22.13 (node:sqlite встроен; на 22.x экспериментальный API). Стенд использует SQLite WAL + synchronous FULL; ack формируется после COMMIT. Запуск — только loopback, owner token передаётся окружением и не кладётся в git/клиент:

```sh
node --test party-game/tests/feedback-sync.test.cjs
KVIP_OWNER_TOKEN='<случайный локальный секрет не короче 32 символов>' node party-game/feedback-sync/local-server.cjs
```

По умолчанию база в `/tmp/kvip-feedback-023a.sqlite`; для повторяемого долговременного локального стенда задайте `KVIP_FEEDBACK_DB` на отдельный путь. Это не долговременное облачное хранилище. `GET /owner/export` с Bearer owner token возвращает агрегаты и максимум 1000 актуальных жалоб; пагинация/полный owner-архив — 023B. Токен не передаётся в ingestion и не вводится в PWA. Браузерный доступ к owner endpoint у стенда запрещён, используйте локальный CLI.

Browser тест сам поднимает одноразовый loopback-сервер, использует настоящий origin приложения и реальные производственные журналы. Модули добавляются **только тестом**, включая после offline reload; в published cache они не появляются. Проверяются инертный gate, CORS/ACK, offline→reload→online, unchanged JSON/private storage, замена/удаление, Web Locks в двух вкладках. Скриншоты не создаются: UI не менялся. Для существующей PWA все прежние Browser/Logic/Gameplay/Smoke/upgrade проверки сохранены.

Будущий adapter 023B должен: дождаться успешного сохранения/удаления/очистки через прежнее ядро; проверить `cardReportsBlocked || cardApprovalsBlocked`; читать через существующие `readCardReports/readCardApprovals`, затем вызвать reconciliation. Повторный poll/boot закрывает окно сбоя после сохранения. Ошибка sync не должна превращать уже сохранённую локальную оценку в ошибку игрового действия. Нельзя читать журналы посреди незавершённой их замены или отправлять их при заблокированном rollback.

Порядок 023B: согласовать провайдера/квоты/retention/доступ; реализовать и проверить production ingress, каталог/antiabuse и owner auth/export; проверить реальные ACK и отказоустойчивость; добавить notice и понятный статус; подключить адаптер с выключенным gate и upgrade-приёмкой; только затем разрешённое включение и отдельный PWA-релиз. Ни merge, ни облачное развёртывание, ни включение отправки не входят в 023A.

### Доказанные дефекты и исправления

1. После ожидания sender-lock клиент мог отправить ранее подготовленное событие, хотя adapter уже заблокировал журналы из-за неподтверждённого rollback. Перед каждым выбором события теперь повторно проверяется доступность и валидность источника. Регрессия сначала воспроизвела лишний POST, затем прошла в Logic и с настоящим Web Lock двух вкладок. Исходные журналы и RAW очереди сохраняются.
2. Ответ с неверным Content-Type или HTTP-ошибкой оставлял непрочитанный поток без отмены. Клиент завершает fetch/AbortController и отменяет непрочитанное тело. Stream-регрессия проверяет 200 с неверным типом, 429 и 503; без точного ACK pending сохраняется.
3. `stop()` во время первого `start()` мог оставить заново установленный polling; параллельные `start()` создавали несколько таймеров, а частые сигналы могли накапливать ожидающие flush. После первого ожидания повторно проверяются stop/timer; автоматические сигналы объединяются в одну выполняемую задачу. Регрессии проверяют остановку во время запроса, два одновременных запуска и 50 сигналов при задержанном ответе.
4. В настоящем CORS браузер не видел Retry-After, хотя Node-проверка видела заголовок. Стенд явно выставляет `Access-Control-Expose-Headers: Retry-After` только для разрешённого origin. Browser проверяет настоящий 503 ёмкости с часовым Retry-After, отсутствие раннего повтора и доставку после срока. Данные исходной SQLite остаются прежними при отказе.

Дополнительно проверены точный ACK после COMMIT, потерянный/устаревший ACK, одобрение→жалоба→удаление, coalescing, долговечный backoff, quota/readback/rollback, повреждение и смена endpoint, лимиты UTF-8/числа записей, owner auth и allowlist приватных полей. Реальный delayed ACK приходит после замены оценки во второй вкладке: сервер сохраняет одну актуальную оценку, новая pending не исчезает. Старые оценки при baseline остаются локально. Новых проблем, требующих изменения опубликованной игры, аудит не выявил.

Межвкладочные гарантии относятся к очереди и отправителю. Прежние синхронные игровые журналы остаются прежними: в 023B все новые mutation/adapter hooks должны разделять согласованную блокировку, чтобы чтение не попадало внутрь межвкладочной замены двух архивов. Не следует объявлять одновременное управление одной партией в разных вкладках поддержанным сценарием.

Полный обязательный CI сохраняет 388 прежних Logic + 3 TASK024 + 29 sync/API, Gameplay/Smoke и весь Browser/mobile/upgrade/offline. Точные окончательные Head и ссылки на завершившиеся push/pull_request запуски публикуются в описании PR #128; одного старого зелёного Head для приёмки TASK025 недостаточно.

## TASK023B — конкретный план production

Ниже проект следующей отдельной задачи. Ресурсы, аккаунты, ключи, платные подписки и endpoint этой работой не создаются. Продуктовое включение требует отдельной приёмки.

### Провайдер и бюджет пилота

Рекомендация: отдельный Cloudflare Worker + D1 на Free, один production D1 и отдельное staging-окружение. Причина выбора — небольшой JSON-ingress с атомарным latest-state SQL, отсутствие постоянно работающего сервера и возможность начать за $0. Supabase предпочтительнее, если потребуются полноценные Auth/Postgres/owner UI: Free имеет 500 MB и паузу после недели простоя; Pro начинается с $25/месяц. Обслуживаемый VPS подходит при уже имеющемся сервере владельца, но требует TLS, обновлений, дискового мониторинга и резервирования; его цену без выбранного сервера определить нельзя.

Workers+D1 Free не означает неограниченное использование: особенно важен лимит **500 MB одной D1**, а не только 5 GB суммы аккаунта. В пилоте не включать платный fallback, R2, Queues или сторонние платные логи. Для owner-доступа первого пилота достаточно защищённого аккаунта Cloudflare и CLI-экспорта D1; отдельный публичный административный endpoint не нужен. Домен для Worker-пилота не обязателен; если позже нужен собственный hostname/Access-панель, его владение и возможную стоимость согласовать отдельно.

Плановая нагрузка для измерения: 1000 принятых изменений/день, до 10 затронутых записываемых строк на событие с индексами и квотами → около 10000 writes/день. Это допущение для benchmark, не гарантия тарифа. Ввести собственный дневной cap принятых событий 10000, квоты на установки/IP, сигналы при 70% дневного бюджета и 350 MB БД; при 400 MB или исчерпании рабочего бюджета — 503 с Retry-After и сохранение очереди на телефоне. Точные пороги после замера скорректировать до включения. Платный Workers от $5/месяц плюс превышения; $5 не является максимумом счёта. Переход на него — только отдельное решение владельца. Проверить доступность аккаунта и условий использования для владельца, ничего не обходить временным чужим аккаунтом.

### Постоянная БД и атомарность

| Таблица | Ключ / содержимое | Правило |
| --- | --- | --- |
| `installations` | installation ID, hash учётного материала установки, status, server expiry | Анонимная установка, без имени/профиля; отзыв и срок жизни определяются сервером |
| `votes` | `(install_id,item_key)`, revision, hash, rating, reason/comment, server timestamps | Одна текущая оценка, только большая revision; deleted оставляет watermark без старого комментария |
| `event_hashes` | `(install_id,revision)`, canonical hash | Повтор того же события не меняет счётчик; другое содержимое той же revision отклоняется |
| `catalog_items` | `(pack_id,pack_version,card_id)` и manifest hash | Проверяемый реестр допустимых ID, включая исторические версии |
| `quota_windows` | scope/key hash/window, count/expiry | Атомарные квоты, общие для экземпляров Worker |
| `rollups` | период/item/rating/reason, count | Обезличенная редакционная статистика с согласованным сроком хранения |
| `schema_migrations` | номер миграции / hash | Воспроизводимые forward-compatible миграции |

Дедупликацию, квоты, запись события и обновление latest vote выполнять атомарно. Node `BEGIN IMMEDIATE` нельзя считать готовым кодом D1: реализовать ограниченный SQL batch с условными UPSERT/ограничениями и доказать rollback при любом конфликте. [D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/) обеспечивает последовательное атомарное выполнение; ошибки откатывают batch. ACK выдаётся только после успешного результата. Не переносить `COUNT(*)` по всей растущей таблице в каждый приём: использовать индексы и счётчики квот. Проверить конкурентные, повторные, переупорядоченные запросы и метрики rows_read/rows_written в настоящем staging D1.

Реестр каталога строится из проверенных сборок, с сохранением исторических manifests и источника версии. Для pack=null нужен отдельный точный legacy-global allowlist известных ID; текст для угадывания ID не используется. Реестр публикуется раньше клиента. Неизвестные/неоднозначные ID получают явную ошибку и сохраняются локально для экспорта; новая панель должна показывать проблему, а не бесконечно повторять запрос. Каталоги игры для этого не редактируются.

### Запросы, накрутка и доступ владельца

До SQL: точный route/method/origin, 2 KiB cap по реально прочитанным байтам, fatal UTF-8, закрытая схема и проверка каталога. Сохранить минимальный wire и отсутствие cookies/referrer. CORS не считать авторизацией или защитой от бота. Дешёвое ingress-ограничение дополняется устойчивыми квотами D1, лимитами регистрации новых установок, глобальным kill switch и метриками отказов. IP для кратких квот — server-side hash с ротацией; не сохранять raw IP/тело комментария в прикладных логах. Оценки считать редакционными сигналами, не голосованием уникальных людей; автоматическое удаление карточек по счётчику не вводить. Challenge при реальной атаке требует отдельного UX-решения.

Для безопасного удаления с телефона и защиты от присвоения чужого UUID в 023B нужен отдельный учётный материал анонимной установки, выдаваемый/проверяемый сервером. Это не owner token и не общий секрет в JavaScript. Ввести versioned registration/auth/delete контракт, срок действия и отзыв; протестировать CORS и upgrade. Текущий v1 UUID-only прототип такую авторизацию не обещает. Нельзя просто опубликовать стенд с синтаксической проверкой UUID.

Доступ владельца в первом пилоте: его собственный Cloudflare-аккаунт с MFA и наименьшими нужными разрешениями. [Полный D1 export](https://developers.cloudflare.com/d1/best-practices/import-export-data/) через Dashboard/Wrangler доступен после его входа, сохраняется владельцем вне публичного git. Будущая web-панель — отдельная авторизация/SSO, проверка подписи, issuer/audience/expiry на сервере и запрет обхода через прямой hostname; просто доверять присланному email/header нельзя. Административные ключи, если потребуются, только в server-side secrets, никогда в HTML/JS/PWA/storage клиента.

Экспорт всей статистики не должен наследовать стендовый LIMIT 1000: согласованный snapshot/cursor, все aggregates/current reports и метаданные схемы/каталога, JSON/NDJSON без выполнения пользовательского текста. Для web-панели — textContent, для возможного CSV отдельно экранировать формульные значения. Полный приватный SQL backup и редакционный экспорт — разные уровни доступа. Оба проверяются без авторизации (отказ) и с владельцем (полный результат).

### Хранение, удаление и уведомление

Предложение для решения владельца: свободные комментарии до 90 дней, актуальные псевдонимные оценки до 12 месяцев, обезличенные rollups до 12 месяцев. Подтверждённое удаление оценки немедленно убирает её из текущих отчётов; минимальный watermark/hash против replay живёт до истечения/отзыва установки, без старого комментария. Удаление установки сначала отзывает её учётный материал, затем стирает votes/event payload и обновляет статистику. Понятно объяснить отличие серверного удаления от очистки данных сайта; очистка сайта сама по себе не удаляет облачную копию и теряет возможность подтвердить владение прежней установкой.

TTL не должен позволить старой offline-очереди воскресить удалённые сведения. Сервер отклоняет истёкший/отозванный материал; новая установка/повторное включение требует явного решения и нового baseline без пересылки старого архива. Отдельно определить срок минимальной revocation-записи до expiry и срок удаления backup/logs. D1 Time Travel на Free сохраняет историю до 7 дней, на Paid — 30; мгновенное физическое стирание из этой истории обещать нельзя. Собственные выгрузки тоже должны истекать по выбранной политике; тест восстановления обязан повторно применить последующие удаления/отзывы до открытия ingress.

Предлагаемый текст перед включением: «Новые оценки будут отправляться владельцу КВИП. В жалобе передаются причина и ваш комментарий; не указывайте личные данные. Имена игроков и результаты партий не передаются. Старые оценки останутся на устройстве». Рядом — политика сроков, отключение и серверное удаление. Формулировку и основание передачи согласовать до публичного включения; этот документ не является утверждённой privacy policy.

### Подключение PWA, развёртывание и откат

1. Владелец выбирает провайдера/Free-бюджет, подтверждает собственный аккаунт, регион/доступность, MFA, сроки, notice и способ owner-экспорта. Секреты в чат/публичный PR не присылаются; вход выполняется владельцем через штатный интерфейс.
2. В отдельной 023B создать staging Worker/D1, versioned schema и catalog manifests, реализовать атомарный ingress/auth/quotas/delete/export/retention. Проверить конкуренцию, сетевые сбои после COMMIT, исчерпание квот, backup/restore с удалениями и публичный отказ owner API. Замерить CPU и D1 rows на Free.
3. После приёмки staging отдельно создать production и owner-доступ. Миграции additive, до них приватный backup. Проверить health и отказ без разрешённого доступа; отправка PWA всё ещё выключена.
4. Подключить адаптер к успешным операциям прежнего архива: save/update/delete/clear → проверка durable результата/rollback → reconciliation. В 023B согласовать блокировки mutation и snapshot между вкладками. Ошибка очереди не отменяет уже сохранённую локальную оценку. Сохранить Web Share/JSON и проверку legacy без ID.
5. UI состояния: «сохранено на устройстве», «в очереди», «подтверждено сервером», «требует внимания». Отдельно показывать historical/localOnly/deferred. Ни пустая очередь, ни HTTP 200 без валидного ACK не означают «всё отправлено». Доставка закрытой PWA ждёт следующего открытия.
6. Выпустить кандидат с подключёнными модулями, но выключенным gate; полный upgrade/offline/geometry CI и физический Android. Затем после согласованного notice и отдельного разрешения включить доставку ограниченному пилоту. Первый opt-in создаёт baseline; автоматического импорта старых архивов нет.
7. Откат: остановить приём серверным kill switch с retryable ответом без ACK, остановить/выключить sender, сохранив архивы и очередь; откатить Worker на совместимую версию. Не откатывать D1 к старому snapshot при открытом ingress — потеряются dedup/watermarks. При аварийном восстановлении сначала закрыть ingress, восстановить БД, применить актуальные revocations/watermarks и проверить, только затем открыть. Базовый endpoint binding не менять незаметно.

Критерий готовности 023B: проверенный реальный backend и приватный доступ владельца, воспроизводимая цена/квоты, каталожная проверка, удаление без replay, согласованный notice, baseline skip-old и физическая приёмка PWA. До этого текущая поставка остаётся выключенным локальным прототипом.
