## Что сохранено в коде

### Идентичность и порядок ролей: `team-format.js`

Самостоятельный чистый контракт `version:1`, `format:'teams-2x2'`. В заголовке — ID партии, две команды с двумя именами, три начальные позиции и явная политика **`excluded-from-duel-profiles`**. Индексы команды, загадывающего, отгадывающего и получателя очков раздельные. Профильных ID здесь нет.

`create(names,{id,random})` проверяет все четыре имени и ID **до** выборки позиций, затем ровно три раза вызывает переданный RNG: первая команда, первый загадывающий команды 1, первый загадывающий команды 2. ID передаёт вызывающая сторона (в будущем `crypto.randomUUID()`), он не занимает один из трёх выборов позиции. Неизвестная версия, поля, пустые/длинные имена, невидимые управляющие символы, дубли после NFKC/регистра/пробелов и распространённые латинско-кириллические двойники отвергаются.

`roles(header,turnIndex)` больше не вызывает RNG. Команда — `(firstTeam + turnIndex % 2) % 2`; внутри неё загадывающий — `(openingSetter[team] + floor(turnIndex / 2) % 2) % 2`. Партнёр получает противоположный индекс внутри **той же** команды. Получатель командных очков — активная команда, независимо от старого выбора setter/guesser. Это контракт получателя, **не реализация начислений или адаптация восьми режимов**.

`turnIdentity` даёт отдельный снимок четырёх индексов для будущей истории. `validateTurnIdentity` отвергает непоследовательные роли и смену получателя. Отображаемые имена нужно выводить через `textContent`/существующий `escapeHTML`, не интерпретировать как HTML.

### Изолированное хранение: `team-storage.js`

Ключ **`kvip:teams-2x2:v1`**, журнал прерванной записи **`kvip:teams-2x2:v1:pending`**, origin-wide Web Lock **`kvip:teams-2x2:v1:write`**. Только эти два ключа доступны модулю. `iskra-party:v1`, его recovery, профили, оценки и долговременная статистика не читаются и не записываются.

Конверт имеет собственные `version`, `kind`, монотонную `revision`, `match` и SHA-256 полезной нагрузки. Хеш выявляет случайное повреждение; это **не подпись и не защита от владельца localStorage**. Размер ограничен 1 MiB UTF-8 для записи и 3 MiB для журнала. Журнал может не поместиться в квоту: тогда действие не считается сохранённым, исходная партия не заменяется.

`create` требует **полный синхронный `validateMatch`**, возвращающий строго `true`. Валидатор обязан проверить настоящий движок, history/replay, суммы, роли, планировщики, каталоги и текущую фазу. Такой производственный валидатор **ещё не реализован**. Проверка одного заголовка не позволяет безопасно включить сохранения. Тестовый `fixtureOnly`-валидатор проверяет исключительно контракт I/O и никогда не должен подключаться к приложению.

В браузере запись выполняется только через настоящий Web Locks API. При отсутствии API модуль блокируется; небезопасного fallback на таймаут/localStorage-lock нет. Для unit-тестов можно передать сериализующий провайдер. Он обязан удерживать блокировку до завершения всех `await` и обслуживать всех писателей этого слота.

Порядок транзакции:

1. Синхронно зафиксировать снимок действия; поздняя мутация объекта вызывающей стороной его не меняет.
2. Под exclusive lock сверить точный `expectedRaw`, отсутствие pending и валидность прежней записи. Другая ревизия/партия, неизвестная версия или повреждение запрещают перезапись.
3. Проверить новый матч и checksum, записать/прочитать обратно журнал с **обоими** RAW.
4. Записать/прочитать обратно новый основной RAW, затем удалить/проверить отсутствие журнала.
5. Считать действие сохранённым только после успешного последнего шага. При сбое сохранить оставшиеся данные и вернуть ошибку; автоматического разрушительного rollback нет.

`load` ничего не нормализует и не пишет. Pending блокирует обычное чтение/запись до отдельной процедуры. `pending` проверяет обе стороны журнала, checksum, последовательность ревизий и принадлежность одному матчу. `recover` требует точный просмотренный журнал и **явный** выбор `keep-before`/`keep-after`. Если основной RAW уже отличается от обеих сторон, повреждён сам журнал или появилась неизвестная версия, восстановление не перезаписывает данные. UI восстановления/экспорта сырой повреждённой записи ещё предстоит реализовать.

Модуль намеренно не имеет команды незаметной замены текущего матча новым ID. Безопасное завершение/архивирование командной партии и освобождение её слота — оставшаяся работа.

## Точная оставшаяся работа

1. **Настоящий versioned engine adapter.** В текущем дуэльном коде `guesser=1-setter`, `awardRecipientIndex` может указывать на соперника, `newGame` резервирует два профиля, `persist` и транзакции review/таймера пишут константу `iskra-party:v1`. Простая замена названий двух сторон командами повредит смысл ролей и статистики. Нужен явный discriminator командной партии, отдельный вход создания/восстановления и slot-aware транзакции. Старые версии правил/сохранений должны оставаться точными.
2. **Полный валидатор командной партии.** Связать `teamFormat`, roundIndex, текущие роли и все history snapshots; повторно вычислять суммы/исходы по закреплённым правилам. Валидировать risk/planners, feedback hold, finish/reply и tiebreak. Для неизвестного формата — защита RAW без миграции. Лишь затем подключать `team-storage` к настоящему матчу.
3. **Новый матч и статистика.** Отдельные options/taskMemory/архив команд внутри нового слота; не вызывать двухпрофильную регистрацию/`saveCompletedProfileResult`. В UI явно написать: «Командные результаты сохраняются в истории этой партии и не входят в личную статистику профилей». Сохранить одновременно незавершённую дуэль. Добавить безопасный архив/новый командный матч/восстановление pending без скрытой потери первой партии.
4. **Реальный шаг Мастера.** Формат «1 НА 1 | КОМАНДАМИ», два блока по два имени и честная валидация, общий preview. Настройку setter/guesser скрыть только в командах; индивидуальная дуэль остаётся прежней. Старый интерфейс и мгновенный opt-out сохранить.
5. **Все восемь режимов.** Существующее математическое ядро базовых наград/усложнений/риска использовать без переписывания исторических версий; командную маршрутизацию очков сделать отдельной версионированной политикой. Не применять дуэльный запрет «Данеток» к командам. Для «Примерно» показать два совместных числовых ответа команд и прежний принцип сравнения, с отдельным shared outcome. Блиц — ровно 3 слова, общий таймер, 2 базовых очка.
6. **Рендер и история.** Сохранить геометрию v88, показать состав/командный счёт, передачу конкретному загадывающему и его партнёру. Review/replay должен использовать командные идентичности; завершённая история остаётся read-only, жалобы на карточки и слова Блица сохраняются.
7. **Автоматическая приёмка.** Настоящие партии обоих форматов: все стартовые позиции, 4/8/12 ходов, все режимы/риск/бонусы, исторические исправления, победа по очкам/ходам, ответный ход/тай-брейк, write failures/concurrency, offline посреди таймера и rollback на точные старые файлы с обеими партиями. Весь прежний CI и новые сценарии для push и pull_request на конечном Head.
8. **Только после полной проверки** подключить модули к HTML/precache и разрешить командный переключатель в Draft. Публикация/merge требуют отдельной приёмки владельца; автоматического включения в production нет.

## Откат текущего WIP

Текущий WIP не меняет игровой runtime. Возврат к TASK 027 или контрольному production не требует конвертации и не изменяет старый слот. Экспериментальные командные ключи оставлять на месте, не вызывать `localStorage.clear()`. Когда реальный командный runtime будет подключён, перед публикацией обязателен настоящий SW upgrade/offline/rollback тест с сохранённой дуэлью и отдельной командной партией; пока этот критерий не выполнен.
